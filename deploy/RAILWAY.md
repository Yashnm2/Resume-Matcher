# Single-service deployment

Resume Matcher is deployed from one GitHub repository as one Docker web
service. The root `Dockerfile` builds the Next.js application and installs the
FastAPI application. At runtime only the host-provided public port is exposed;
FastAPI stays on the container loopback network and Next.js proxies `/api`,
`/docs`, `/redoc`, and `/openapi.json` to it.

This is the supported production topology. `Dockerfile.backend` and the worker
scripts are retained only for advanced operators who intentionally split the
Job Scout workload.

## Railway

1. Push this repository to GitHub.
2. In Railway, choose **New Project → Deploy from GitHub repo**.
3. Railway detects the root `Dockerfile` and `railway.toml` automatically.
4. Add a volume mounted at `/app/backend/data` so SQLite data and encrypted
   settings survive redeployments.
5. Add `LLM_API_KEY` in Railway Variables, or configure a key later in the app's
   Settings page. Optionally set `LLM_PROVIDER` and `LLM_MODEL`.
6. Generate a public domain and open `/api/v1/health` to verify the deployment.

Do not set `NEXT_PUBLIC_API_URL` or `BACKEND_ORIGIN` for this topology. Their
defaults deliberately keep browser traffic same-origin and the API private.
Railway supplies `PORT`; the startup script binds Next.js to that port and also
uses it for internal PDF rendering.

If you attach Postgres with `DATABASE_URL`, migrations run automatically before
startup. A database is optional for the regular single-user experience.

## Render

The root `render.yaml` now deploys the same combined `Dockerfile` instead of the
old backend-only image:

1. In Render, create a **Blueprint** from the GitHub repository.
2. Set `LLM_API_KEY` when prompted. `ENCRYPTION_SECRET` is generated by Render.
3. Deploy and verify `/api/v1/health` and then `/`.

Render's free filesystem is ephemeral. For durable data, either attach a disk
at `/app/backend/data` on a compatible paid plan, or configure
`HF_STATE_REPO_ID` and `HF_TOKEN` so the built-in snapshot service can restore
the SQLite database after a restart.

## Required and optional variables

| Variable | Required | Purpose |
| --- | --- | --- |
| `LLM_API_KEY` | For hosted AI | Provider credential; may instead be entered in Settings |
| `LLM_PROVIDER` | No | Defaults to `openai` |
| `LLM_MODEL` | No | Uses the provider default when empty |
| `ENCRYPTION_SECRET` | Shared deployments | Stable key used to encrypt stored provider credentials |
| `DATABASE_URL` | No | Enables Postgres instead of local SQLite |
| `AUTH_REQUIRED` | No | Enables Supabase JWT authorization |
| `NEXT_PUBLIC_SUPABASE_URL` | With auth | Public Supabase project URL, supplied at image build time |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | With auth | Public Supabase key, supplied at image build time |

## Why the old deployment failed

The repository contained two incompatible deployment stories:

- `render.yaml` built `Dockerfile.backend`, so Render exposed only FastAPI and
  never built or served the user interface.
- the advanced Railway guide asked for separate frontend, API, Celery worker,
  beat, Redis, and Postgres services even though the root Dockerfile already
  supported the normal product as one service.
- the root startup path did not apply Alembic migrations when `DATABASE_URL`
  was present.
- PDF generation assumed the frontend always ran on port 3000, but Railway and
  Render inject their own public port.

The checked-in manifests and startup script now agree on the one-service model.

## Local production-equivalent check

```bash
docker compose up --build
curl http://localhost:3000/api/v1/health
```

The app, API, API documentation, and PDF print routes should all be reachable
through port 3000. Only one container needs to be deployed or restarted.
